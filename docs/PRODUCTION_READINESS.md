# Production Readiness Tracker

Living record of the 2026-08-21 production-readiness and security audit, updated as controls are implemented or re-verified. This file is the source of truth — AGENTS.md §34 states the same thing: a written rule is not proof a control exists.

**Statuses used:** `Implemented` · `Partially Implemented` · `Not Implemented` · `Not Applicable Yet` · `Cannot Verify`

**How to read "Verification status":** who checked this, when, and how — not just whether it currently looks true. A row is only `Implemented` when its evidence was actually re-read/re-run at the date shown, not recalled from a prior audit.

---

## How this tracker stays accurate

- **Every PR** that touches an endpoint, table, or workflow listed below updates the corresponding row in the same PR — not a follow-up.
- **Every CI run** exercises whatever is wired into `npm test` (see CI-01/TEST-01 below) — a green CI run is evidence only for what actually ran.
- **Before every deployment**, re-check any row whose evidence lives outside this repo (Supabase dashboard settings, GitHub branch protection) — CI cannot verify those.
- **Monthly, post-launch**, re-verify every `Cannot Verify` row against the live project, and spot-check a few `Implemented` rows against current code to catch silent regressions.
- A control may only be marked `Implemented` when the evidence cited was read or executed at the "Last verified" date — not inferred from this document's own history.

### DB tests in CI — investigation result

**Decision: left out of CI in this phase.** The five safety conditions given for this task can be satisfied in principle, but the sixth — *"the configuration is reliable on GitHub-hosted runners"* — cannot be proven from this environment:

- Running `tests/db` requires the **full local Supabase stack** (Postgres, GoTrue, PostgREST, Storage — this repo's tests exercise real RLS through real per-user sessions, not mocks; see `tests/db/helpers.mjs`). Starting that stack means running `supabase start`, which pulls and runs several Docker containers.
- GitHub-hosted `ubuntu-latest` runners have Docker available, and the official `supabase/setup-cli` action plus `supabase start` is a documented, commonly-used pattern — but its reliability depends on image-pull latency, the standard runner's 2-core/7GB resource ceiling, and known community reports of intermittent slowness/flakiness from heavier auxiliary services (analytics/logflare, edge-runtime, imgproxy) that this project's tests never actually need.
- Proving reliability requires an actual run against a GitHub-hosted runner — which this controlled, no-push task cannot do (pushing/triggering Actions is out of scope until you approve it). Per your instruction not to improvise past that point, DB tests stay out of CI until reliability is demonstrated with a real run.

**Safest path forward (Phase 2+, not implemented now):**
1. Add a **separate**, initially **non-required** CI job (`db-tests`), so a flaky run never blocks merges while it's being proven out.
2. Use `supabase/setup-cli@v1` pinned to a specific version, then `supabase start` (excluding services this project's tests don't use, if the installed CLI version supports selective startup — e.g. `--exclude analytics,imgproxy,edge-runtime`) to keep the stack minimal and faster to boot.
3. Read connection details from `supabase status -o env` **within the job** (never committed) and export them as job-scoped env vars for `npm run test:db` — no secret is ever stored in the repo or in GitHub Secrets, since these are ephemeral local-only credentials generated fresh per run.
4. Run `npm run test:db`, then `supabase stop` (the runner's teardown would also discard everything regardless).
5. Watch it run green on several real PRs before promoting `db-tests` to a required check.

### Part A — Error classification (Phase 3): evidence, fix, verification

**Root cause, confirmed via real isolated n8n executions this session (not assumed from Phase 7's own findings, independently re-derived from n8n's source and from direct testing):**

1. n8n's Code-node `continueOnFail` capture strips a thrown `Error`'s message down to the text after its **last colon**, erasing any `PERMANENT:`/`RATE_LIMIT:`/`RETRYABLE:` prefix. A *return value* (never thrown) is passed through untouched — this is the mechanism the proven `errorKind` convention relies on, and it was re-confirmed, not just cited, before implementing.
2. A plain `httpRequest` node (`Call OpenAI`) with `continueOnFail: true` and no "never error" response option never surfaces a `statusCode` at all on a non-2xx response — confirmed directly via `p3-test-never-error.mjs` against a real local n8n container and a mock server returning HTTP 429. Setting `options.response.response: { fullResponse: true, neverError: true }` makes the node's own `executionStatus` "success" for **any** status code, with the real `statusCode` present in its own output (`{ statusCode, headers, body, statusMessage }`) — confirmed via that same real execution. This is a new finding beyond Phase 7's own investigation, and beyond what the live patch addresses (the live patch never configures this option; `Parse AI Response`'s 429/500+ branches would still be unreachable there too).

**Fix implemented** (`fix/cv-worker-error-classification-refactor`, committed `4828839`, both `n8n-workflows/cv-analysis-worker.ts` and `.json`):

- Every one of the file's 20 `throw new Error(...)` sites — across `Validate CV Context`, `Handle Context Failure`, `Normalize CV Context`, `Merge Preference Data`, `Build OpenAI Request`, `Parse AI Response`, `Validate CV Ownership`, and `Build Task Update` — converted to a `return [{ json: { error, errorKind } }]` structured value (`errorKind` one of `'permanent' | 'retryable' | 'rate_limit'`), matching the already-proven live-patch convention node-for-node.
- `Call OpenAI` gained the `fullResponse`/`neverError` options above; `Parse AI Response` updated to read `aiResponse.body.choices[...]` (the new wrapped shape) and `aiResponse.statusCode` (now real for every response, not just a successful one).

### Part B — P0 privacy decision memo (Phase 2)

**Do not implement any of the options below without explicit approval — this section is the required memo, not an implementation.**

The question: CV text, prompts, and extracted personal data are visible in n8n's own execution history (database rows written by n8n itself, independent of this app's Supabase tables) for every node that handles them, for as long as that execution record is retained. Phase 7 already reduced this from ~5 duplicate copies down to 2 irreducible ones (`Normalize CV Context`'s canonical copy, `Build OpenAI Request`'s `openAIBody`) — this memo is about what to do with those remaining copies, plus the broader retention question Phase 7 did not evaluate end-to-end.

This session traced the complete retention mechanism by reading n8n's own source directly inside the running container (`to-save-settings.js`, `execution-lifecycle-hooks.js`), not by inference, and ran real executions against each candidate setting:

- `saveDataSuccessExecution` / `saveDataErrorExecution` (workflow `settings`, `'DEFAULT' | 'all' | 'none'`, falling back to instance-level `GlobalConfig.executions.*`) govern retention **only for non-manual (real scheduled/production) executions** — confirmed by reading `hookFunctionsSave`'s own branch logic.
- For **manual-mode** executions (`/rest/workflows/{id}/run`, the only mode this session's test methodology could use without activating the live schedule trigger), those two settings are **entirely ignored**; a separate setting, `saveManualExecutions`, governs retention instead.
- There is **no partial/metadata-only retention tier**. Setting the relevant flag to suppress persistence performs a full soft-delete of the execution record — confirmed directly: `includeData=true` against a suppressed execution afterward returns `{}` (no status, no timestamps, nothing), not a redacted summary.
- `settings.errorWorkflow` (n8n's built-in mechanism for routing a failure to a separate, deliberately-sanitized handler workflow) is only invoked inside the same `!isManualMode` branch as the two save settings above — this session's manual-mode testing could not confirm it fires at all (a real test produced 0 error-workflow executions), so its effectiveness for the actual production (scheduled-trigger) path remains **unconfirmed**, not assumed working.

**Option A — n8n execution-data retention settings** (`saveDataSuccessExecution: 'none'`, `saveDataErrorExecution: 'none'` on the workflow, plus the equivalent instance-level default for non-manual runs; `saveManualExecutions: false` separately for manual/test runs).
- *Security guarantee*: for whichever mode the setting actually covers, this is a complete, structural guarantee — nothing is persisted, not partially, not redacted. Verified directly.
- *Limitation*: it is all-or-nothing. Suppressing success-execution data also removes every other diagnostic signal (timing, which branch ran, non-sensitive metadata) that Phase 6/7's own observability work (and AGENTS.md §19/§30) depends on for debugging a production incident — there is no way to keep "safe" fields and drop only the sensitive ones at this layer. The `errorWorkflow` mitigation (keep a sanitized summary even with error-execution data suppressed) is the standard way to recover *some* of that, but its real-world firing behavior for this workflow's actual trigger mode is unconfirmed, not just undocumented.
- *Implementation complexity*: lowest of the three real options — a workflow-`settings` change plus (if the production trigger needs it) one instance-level config value. No code change to any node.
- *Operational implications*: every future "why did task X fail" investigation loses execution-history as a diagnostic tool for this workflow specifically, unless the `errorWorkflow` mitigation is built and separately verified to actually fire on a real (non-manual) failure — a verification this session's safety rules (no live n8n activation) could not perform.
- *Backward compatibility*: no schema or API change; purely an n8n instance/workflow configuration value.

**Option B — Sensitive-data minimization while preserving real execution** (Phase 7's own prior work, already at its practical limit).
- *Status*: already maximally implemented (`fix/cv-worker-privacy-hardening`, `53bae20`) — every duplicate copy with zero functional loss has been removed. The two remaining copies are not removable by this strategy: `Normalize CV Context` must hold the canonical CV text for every downstream node to read it by name (removing it would require restructuring the whole pipeline's data-flow contract), and `Build OpenAI Request`'s `openAIBody` must contain the literal outgoing OpenAI request body, in full, because **n8n itself is the component making that authenticated call** — there is no node boundary inside n8n where that payload can exist without also being that node's own persisted output.
- *Why this session did not find a way to extend it further*: this session specifically tested the one idea that could have eliminated the `openAIBody` copy without a new service — merging `Build OpenAI Request` + `Call OpenAI` into a single Code node, so the prompt is built and consumed in one node's local variable rather than becoming a separate node's persisted output. This was **empirically disproven**, not just assumed impractical: a Code node's `this.getCredentials(...)` throws `"this.getCredentials is not a function"` (confirmed via a real execution error), and `this.helpers.httpRequestWithAuthentication` — despite appearing in `Object.keys(this.helpers)` — throws `"The function \"helpers.httpRequestWithAuthentication\" is not supported in the Code Node"` when actually called (also confirmed via a real execution error). There is no way to attach the real OpenAI credential to an authenticated outbound call from inside a Code node on this n8n version. (A local JS variable that is only used to build an *unauthenticated* `this.helpers.httpRequest` call, never returned, genuinely is never persisted — confirmed via a separate real test — but that fact is moot here since the real OpenAI call must be authenticated.)
- *Security guarantee*: strong for everything this strategy can reach (confirmed via a real marker-trace execution that the removed fields are genuinely gone) — but it provably cannot reach the two remaining copies, by the architecture of what "n8n calls OpenAI" means.
- *Implementation complexity / operational implications / backward compatibility*: none further to do here — this option is exhausted, not partially applied.

**Option C — A narrowly-scoped authenticated backend proxy / server-side AI execution boundary** (move the actual OpenAI call out of n8n into a new internal endpoint this app's own backend owns, mirroring how Workflow 02 already delegates prompt-building to `prepare-rerank`; n8n would call it with only a task reference).
- *Security guarantee*: this is the only option that can eliminate the `openAIBody` copy entirely — the CV text would never need to pass through, or be returned by, any n8n node at all; n8n's own execution history would carry a task ID, nothing else.
- *Implementation complexity*: a genuine architectural change — a new authenticated internal API route, its own input validation/auth/rate-limiting (AGENTS.md §27/§28/§30), a new trust boundary between n8n and this app's backend, and a new test surface (unit + workflow + a real integration path). Not a contained fix.
- *Operational implications*: n8n's job shrinks to orchestration only (claim task → call internal endpoint → write result) — closer to how Workflow 02 already works, which is a maintainability argument in its favor, but it is still new infrastructure that needs its own monitoring, timeout/retry design, and idempotency guarantee (a duplicate call must not double-charge OpenAI or double-insert an analysis row).
- *Backward compatibility*: no existing consumer breaks (the `cv_analyses` row shape, task lifecycle, and retry semantics are unchanged) — but it is a new moving part, not a config change.
- **Not attempted this session**, per this task's own explicit instruction not to silently make this call. This is the recommended path if full elimination of the remaining exposure is required, but it needs its own dedicated design/approval pass, not a decision folded into this memo.

**Option D — Code-node merge (eliminate `Build OpenAI Request` as a separate persisted node by inlining prompt-build + OpenAI call together)**: **ruled out** — see Option B's own sub-finding above. Kept as its own labeled option only because the task's framing asked for A/B/C/D explicitly; it collapses into "Option B is exhausted," not a distinct path forward.

**Recommendation**: do not adopt Option A as currently specified — its all-or-nothing retention tradeoff and the unconfirmed `errorWorkflow` mitigation make it a net loss for a workflow this session is simultaneously trying to make more diagnosable (Part A above), not less. Option B is already fully applied; no further action needed there. **Option C is the only path to full elimination of the remaining exposure**, and is recommended as the next step *if* the remaining `openAIBody` copy is judged unacceptable to leave as a documented, narrowly-scoped residual risk — but it is a real architectural change requiring its own explicit approval, design review, and test plan, not something to fold into this fix's scope. Absent that approval, the residual exposure (one copy of the CV text, in the one node that must make the authenticated call) should be tracked as a known, accepted P1 limitation — a narrower and more honest framing than Phase 7's prior P0 label, now that the reducible portion is fully gone and the irreducible portion's cause is fully understood rather than merely described.

**Required approvals before any further privacy change**: explicit sign-off on Option C's architectural design (new endpoint, its auth/rate-limit/idempotency model) before any implementation begins; separately, explicit sign-off on Option A's retention-settings tradeoff if that path is ever preferred instead (it is not the recommendation here, but is included because the task asked for it to be evaluated, not dismissed).

### Part D — Audit: do Workflows 02 (job matching) and 03 (cover letter generation) share this defect class? (Phase 6, read-only)

**No code was modified in either workflow for this audit.** Finding: **neither workflow shares this defect class, for a clear architectural reason** — both were built using a fundamentally different error-handling design than the CV Analysis Worker, one that structurally cannot trigger n8n's Code-node `continueOnFail` colon-stripping behavior at all:

- Workflow 02 has exactly **one** Code node (`Build Task Completions`) in its entire 20+-node graph, and it never throws — it always `return`s a clean array, with no `PERMANENT:`/`RETRYABLE:`/`RATE_LIMIT:` string-prefix convention anywhere in the file (confirmed via a direct grep across the full `.ts` source: zero matches). Workflow 03 has **zero** Code nodes at all — every node is `httpRequest`/`set`/`splitOut`/`wait`.
- Every `httpRequest` node in both workflows uses n8n's **native** `onError: 'continueErrorOutput'` + `retryOnFail: true` + `maxTries`/`waitBetweenTries` instead of the CV worker's hand-rolled `continueOnFail: true` + read-`.error`-and-classify-by-string-prefix pattern. A transient failure (timeout, 5xx, rate limit) is retried by n8n's own engine, up to 3 times with backoff, before the workflow's own logic ever sees it — there is no classification decision encoded as a thrown `Error` inside a Code node anywhere for this mechanism to corrupt.
- All business-rule-sensitive logic (discovery, eligibility, grounding/prompt-building, persistence, re-validation of approval status) is delegated to the app's own TypeScript backend endpoints (`/api/internal/matching/*`, `/api/internal/cover-letters/*`) — real Node.js code that never passes through n8n's Code-node sandbox or its `continueOnFail` capture mechanism at all. Any classification those endpoints perform happens entirely outside n8n's reach.
- Neither workflow has any logic that reads a specific numeric `statusCode` value off an `httpRequest` node's output for branching — `Build Save Rerank Request`/`Build Save Request` read `$json.choices[0].message.content` directly from a successful response; a failed `Call OpenAI Chat` is routed to its error output branch and just logged generically (`$json.error?.message`), with no permanent-vs-retryable distinction at all, by deliberate design (Workflow 03's own sticky note: "A failed attempt is never recorded — the match is simply re-offered as a candidate on the next run"). So the second sub-defect (missing `statusCode` without `neverError`) is also moot here — nothing ever needed that value in the first place.

**Confirmed defects found**: none. **Potential risks flagged for awareness, not confirmed as defects**: none beyond what Phase 5/6's own prior reports already covered for these two workflows (the rerank-failure observability gap, still open per that report) — this audit did not re-open or re-scope that item.
