## Phase 01 — Location normalization

- **Branch**: `phase/01-location-normalization`, forked from `main` @ `dc8c2c1`.
- **Files added**:
  - `src/lib/ingestion/normalizeLocation.ts` — pure, deterministic `normalizeLocation()`. Input: raw location string + optional provider work-arrangement hint. Output: `rawLocation`, `countryCode` (ISO 3166-1 alpha-2, matches `public.countries.code`), `city`, `workArrangement` (matches `public.jobs.work_arrangement` check constraint: `remote | onsite | hybrid | flexible`), `remoteScope` (free-form, matches `public.jobs.remote_scope`'s intentionally-unconstrained design), `relocationSignal` (`true | false | null`), `locationConfidence` (`high | medium | low`). No DB access, no network, no AI. Also exports `isLowConfidenceLocation`, `isGccCountryCode`, `isMenaCountryCode` helpers for Phase 02's eligibility logic to reuse.
  - `tests/unit/normalize-location.test.mjs` — 27 tests covering: null/empty input, real registry-derived Lebanon/Saudi/Qatar/Kuwait/UAE city+country strings, work-arrangement detection (remote/hybrid/onsite/flexible, provider-hint precedence), remote-scope detection (worldwide/region:gcc/region:mena/country-scoped/no-scope), multi-region fail-closed behavior (never guesses a single country from ambiguous text), relocation-signal detection (positive/negative/unmentioned), and determinism (same input ⇒ deep-equal output).
- **Design decisions and why:**
  - Country/city dictionary is deliberately scoped to the product's five supported markets (Lebanon, Saudi Arabia, Qatar, Kuwait, UAE) plus a short list of high-frequency international-remote-scope countries (US/UK/Canada/Germany/India/France) — extending coverage later means adding dictionary rows, not touching calling code (AGENTS.md §16 maintainability guardrail).
  - Multiple distinct countries detected in one string (e.g. "Beirut, Dubai, or Riyadh") never collapses to a single guessed country — `countryCode`/`city` are `null` and confidence is `low`, so Phase 02's hard-eligibility logic fails closed on it rather than trusting a coin-flip pick.
  - A bare `"Remote"` with no scope signal is `medium` confidence (a real, partial signal), not `low` — reserving `low` for genuinely unrecognized/ambiguous text. This distinction matters for Phase 02, which is expected to treat `low` as "needs human review before matching," not `medium`.

- **Design decisions and documented assumptions** (AGENTS.md §15/§17: "choose the conservative reversible implementation, document the assumption, continue"):

Rationale: that tier's own name and its position as the widest Pro option imply "show the widest net," with actual applicant-eligibility nuance left to the job description/match reasoning, not a hard gate. - **Schema/architecture investigation first** (AGENTS.md §17): read `docs/job-ingestion-pilot.md` (the existing n8n pilot orchestrator's proven design — dedup_scope upsert, stale-close AND-gate, retry/backoff) and the full `docs/job-ingestion-database-readiness-audit.md` history (Sections 21-23), then the actual current migrations: `20260809090030_create_jobs.sql`, `20260914120000_add_jobs_freshness_and_geography.sql`, `20260914150000_create_companies_and_company_sources.sql`, `20260915170000_add_jobs_source_specific_dedup_key.sql`. Conclusion: every piece of infrastructure this phase needs already exists in the database — `companies`/`company_sources` (with `review_status` gating), `jobs.source_id`, and the generated `jobs.dedup_scope` column with its full (non-partial) `jobs_dedup_scope_external_id_key` index, which is the only index PostgREST's `.upsert({ onConflict })` can actually target. This phase builds the reusable **TypeScript** pipeline around that existing schema — not a second copy of the n8n pilot's Code-node logic, and no new tables/columns.
- **Files added**:
  - `src/lib/ingestion/rawProviderJob.ts` — pure, DB-free: `RawProviderJob` (the generic contract any Phase 04 adapter must produce), `validateRawProviderJob()` (rejects — never inserts with a placeholder — a job missing a required field or with a malformed application target; a LinkedIn-sourced job may never resolve to an email-only application target, per AGENTS.md §7), and `mapRawProviderJobToJobRow()`, which calls Phase 01's `normalizeLocation()` to populate `country_code`/`city`/`remote_scope`/`work_arrangement` — a genuine improvement on the n8n pilot, which left those hardcoded `NULL` as a documented limitation. A location that normalizes to `low` confidence is still ingested (never silently dropped) but mapped to `status: 'pending_review'` instead of `active`, using the status value the 2026-09-14 audit's own P0 remediation added for exactly this case; Phase 02's `checkJobEligibility` is what actually keeps a `low`-confidence job hidden from users, so this is not a duplicate gate.
  - `src/lib/ingestion/ingestSourceBatch.ts` — the DB-touching orchestration for one `company_sources` row per call: `verifySourceForIngestion()` re-checks `review_status` live on every call (never trusts a caller-supplied "this source is approved," mirroring the pilot's own "re-verifies provenance every run" design), and `runIngestionBatch()` validates + maps + bounds (`maxJobsPerSource`) + idempotently upserts (`onConflict: "dedup_scope,external_id"`) + closes source-scoped stale jobs — gated, exactly like the pilot, on the fetch having been complete and *not* truncated, so a bounded/partial page can never mark still-active jobs unavailable just because they fell outside this run's cap. Supports `dryRun` (validates and reports, writes nothing). Throws on an unexpected database error rather than reporting false success (AGENTS.md §18/§30) — classifying/retrying a thrown error across many sources is explicitly left to the Phase 04 orchestrator, which is this module's only intended caller shape (one source, one call).
  - `tests/unit/raw-provider-job.test.mjs` — 19 tests: every rejection reason, LinkedIn-email-forbidden, geography population vs. the pilot's null, low-confidence → `pending_review`, application-method derivation, provenance passthrough, determinism.
  - `tests/db/ingestion-core-batch.test.mjs` — 8 tests run against the **real local Postgres** (not mocked): unapproved-source rejection with zero writes, nonexistent-source rejection, live re-verification (a source approved at call time but flipped to `blocked_or_unsafe` mid-test is rejected on the next call), `dry_run` writes nothing, mixed valid/invalid jobs are counted and only valid ones persisted, an idempotent retry updates the same row (never a duplicate) and always uses the live `company_sources.company_name`, a truncated run never closes jobs outside its own page, and a complete run correctly closes a job absent from the latest fetch with `status_reason: 'not_found_in_latest_ingestion_run'`.

No n8n workflow. No content-hash/cross-source dedup (still an unmade product decision per the audit's own Section 19, unchanged). No `automation_tasks` wiring — this module is called directly, not yet claimed from a queue.
