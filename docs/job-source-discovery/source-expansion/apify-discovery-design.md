# Apify-Based Company-Discovery — Design Notes

**Status: IN PROGRESS — design notes, not an implementation. No Apify actor has been run and no automation has been built or activated under this task.**

## 1. Purpose

Evaluate realistic Apify approaches for turning the source catalog (`source-catalog.csv`) into a repeatable company-discovery pipeline, without running a large or paid job and without spending Apify credits. This document records actor candidates, their input/output shape, geography/category support, pagination behavior, expected noise, pricing/credit risk, and technical/compliance limitations — evaluated by reading each actor's public listing/documentation, not by executing it.

## 2. Evaluation criteria applied to every candidate actor

- **Input/output format** — what the actor accepts (search term, location, category, URL list) and what it returns (JSON fields available).
- **Geography and category support** — whether it supports Lebanon/Gulf granularity (city-level for UAE) and business-category filtering.
- **Pagination** — how it handles result sets beyond the first page, and whether that scales safely within a bounded run.
- **Expected noise and duplicates** — likely rate of irrelevant, closed, or duplicate listings, based on the actor's documented behavior and category.
- **Pricing/credit risk** — Apify pricing model for the actor (per-result, per-compute-unit, subscription) and realistic cost for a bounded pilot vs. a full run.
- **Technical limitations** — rate limits, CAPTCHA/anti-bot exposure, data freshness.
- **Compliance limitations** — ToS restrictions of the underlying platform, and this project's own hard rule of never scraping or automating LinkedIn.
- **Suitability for the future workflow** — whether the actor's output could feed the existing registry schema (`master-company-registry.csv` fields) with minimal transformation.

## 4. Cross-market recommendation

All 6 markets are now complete. Ranked by realistic near-term value across the whole project:

1. **Himalayas' official API (International Remote)** — the single best finding of the entire project: free, documented, no-auth, structured, with genuine per-job location-restriction data. No actor needed. If this project builds exactly one automated discovery pipeline first, this should be it.
2. **`blackfalcondata/bayt-scraper`** — reused across all 5 country markets (Lebanon, Saudi Arabia, UAE, Qatar, Kuwait) without needing re-evaluation each time; the most broadly useful paid actor found, given Bayt's regional MENA coverage and consistently cheap pay-per-event pricing (~$1/1,000 results).
3. **`blackfalcondata/gulftalent-scraper`** — the second-most broadly reusable actor, confirmed to cover the same 5 country markets in a single documented actor.
4. **`jobs.workable.com/search/[country]/`** — a genuinely reusable pattern discovered in the Kuwait pass: rather than guessing which employers in a given market use Workable, this single search-results URL structure could be crawled per-country to surface every Workable-hosted employer in one pass. Not yet tested for markets beyond Kuwait, but the URL pattern is generic.
5. **Curated startup/company list pages** (GrowthList.co for Saudi Arabia, Failory for Kuwait, the GitHub established-remote list for International Remote) — consistently the single highest new-candidate-yield source type across every market that had one (94-97% new-candidate rates), at near-zero cost (one static page, no pagination fight) — but each carries its own data-quality caveat (GrowthList's paid-tier gate, Failory's startup/state-enterprise miscategorization, the GitHub list's "hires globally" claim not being verified per-country) that any future automated use must account for.
6. **Official government/regulator registers with no login** (Qatar's QFCRA, Kuwait's CBK) — small, precise, and genuinely official, though this project's samples of them skewed toward companies already known (large multinational banks) rather than new candidates; still worth a bounded future crawl for the less-prominent entries.
7. **EOR/payroll platforms as infrastructure evidence, not job listings** (Deel, Remote.com, Globalization Partners) — don't themselves list jobs, but their explicit Lebanon-support confirmations are valuable corroborating evidence when assessing whether any specific employer's "we hire globally" claim is operationally plausible for Lebanon.
8. **`apify/website-content-crawler`** — the necessary fallback everywhere else, used consistently across all 6 markets for single/low-page sources without a dedicated actor; lowest confidence, highest effort, last resort per source, exactly as characterized in every per-market section above.

**Consistently NOT recommended:** any LinkedIn actor (excluded on policy grounds in all 6 markets); Google Maps Scraper for International Remote specifically (structurally mismatched to a market of employers without fixed offices, unlike the 5 country markets where it remains a viable geography-based gap-filler).

- No paid or large-scale job was queued.

### International Remote

**Status: COMPLETE (2026-09-04).**

This pass differed from the 5 country passes in kind, not just degree: instead of chambers, government registries, and industrial cities, the relevant sources are remote-job boards, EOR/payroll platforms, and talent marketplaces — and the central risk is not "can we find the company" but "does 'remote' actually mean Lebanon-eligible," per this task's explicit eligibility taxonomy.

**The headline finding: Himalayas has a free, official, documented, no-auth JSON API with genuine country-level filtering**, including a dedicated Lebanon page. This is qualitatively different from every other source found in this project — no scraping actor is needed at all, and it directly surfaced this pass's strongest single piece of Lebanon-eligibility evidence: a Greenpeace International internship explicitly labeled "(Lebanon-only position)" in Himalayas' own structured data.

**A second major finding: the EOR/payroll infrastructure for hiring in Lebanon is real and mainstream**, not a rare edge case. Three major providers — Deel, Remote.com, and Globalization Partners — were each independently confirmed (2 via direct WebFetch) to explicitly support Lebanon, with Remote.com's claim being the strongest (it states it owns its own local legal entity in Lebanon, not merely third-party contractor-payment support). This doesn't confirm any specific employer's eligibility, but it establishes that the underlying "can this actually be done" question has a real, positive, well-documented answer.

**A key classification finding, directly addressing this task's explicit employer-vs-platform requirement:** Arc.dev, Turing, and micro1 were all investigated and correctly classified as talent marketplaces / recruiting platforms rather than direct employers — in micro1's specific case, a "BigLaw Lawyers" posting that appeared on Himalayas' Lebanon-filtered results turned out, on closer investigation, to be micro1 (an AI-recruiting/EOR platform) placing candidates with client law firms, not micro1's own internal legal team. This is exactly the kind of misclassification risk this task warned against.

Recommended approach if this project ever proceeds to a bounded, approved pilot (not authorized under this task — research/design only):

1. **Build directly against Himalayas' official API** — the only source in this entire 6-market project where "prefer the official API over scraping" has a clean, complete, free answer. Use the `country` and `locationRestrictions` fields to do real per-job Lebanon-eligibility filtering, not just a country-page URL that may include worldwide-open roles (see the important caveat below).
2. **Treat the existing registry's We Work Remotely, RemoteOK, and Remotive rows' documented APIs/RSS feeds as the next tier** — already confirmed in prior rounds, not re-litigated this pass, with Remotive's free-tier-only caveat respected.
3. **Do NOT rely on the GitHub established-remote list, Deel/Remote/G-P marketing pages, or the Ashby ecosystem for per-job Lebanon eligibility** — these are valuable for *discovering companies* (confirmed via the GitHub list's genuine freshness and the EOR platforms' explicit Lebanon confirmations) but none of them assert eligibility at the individual-job level the way Himalayas' API does.
4. **NaTakallam remains blocked for a third consecutive research pass** — this is the existing registry's own explicitly-flagged top manual-recheck priority, and automated retries are no longer a productive use of effort; a human browser visit or a citable press URL is needed.

An important methodological caveat surfaced this pass, worth stating plainly: **Himalayas' "Lebanon" country filter almost certainly includes worldwide-open roles that don't exclude Lebanon, not only roles that specifically target Lebanon** (the 2,119-result count for a single small country is implausible as a Lebanon-specific figure). Every pilot candidate sourced from this filter was therefore conservatively classified `timezone_compatible_but_location_unclear` rather than `explicitly_hires_in_lebanon`, except the one listing (Greenpeace) whose own title explicitly stated a Lebanon-only restriction — a concrete illustration of why this task's stricter 8-value eligibility taxonomy matters in practice, not just in principle.
